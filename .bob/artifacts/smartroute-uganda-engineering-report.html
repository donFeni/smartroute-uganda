1 · Original Problems Discovered
🔴 Critical — Road report markers not appearing on the map
MapStateController held _markers as an empty list. SmartRouteMap rendered visibleMarkers from that list but nothing ever called loadReportMarkers() in the main map context. The Road Reports map tab did call it, but the main MapScreen, home preview and route planner preview did not.
🔴 Critical — New reports submitted via CreateReportScreen never appeared on map
When a user submitted a report, it was added to RoadReportsProvider correctly, but MapStateController was never notified to refresh its marker list.
🟠 High — Tapping a report marker on MapScreen had no "View details" action
MarkerInfoCard accepted an optional onViewDetail callback but it was never wired in MapScreen. Users could tap a pin and see the info card but had no way to navigate to ReportDetailScreen.
🟠 High — Route selection did not update the map polyline highlight
_RouteResultsList loaded route geometries once using route.isRecommended for the selected flag. When a user tapped a different route card, the map continued showing the originally recommended route highlighted.
🟡 Medium — Map screen UI overlap: preset chips and demo badge at same bottom position
Both _PresetChipsRow and _DemoBadge were positioned at bottom: paddingBottom + 16. They visually overlapped. Also, preset chips were shown even when a marker info card was visible at the bottom, stacking them together.
🟡 Medium — Road Reports map view had no "View details" action on marker taps
_ReportsMapView's MarkerInfoCard also lacked the onViewDetail callback, same issue as MapScreen.
🟡 Medium — Route planner map geometry used wrong selection state on rebuild
The loadRoutesFromOptions helper always used route.isRecommended regardless of which route the user had selected. Replaced with inline geometry construction that reads planner.selectedRoute?.id.
🔵 Info — NDK installation corrupted on build machine
Android NDK 28.2.13676358 had a missing source.properties file. Resolved by deleting the corrupted NDK directory; Gradle auto-reinstalled it on the next build attempt.
🟡 Build machine — C: drive at 0 bytes during APK compilation
The build machine has a 100 GB C: drive that was completely full. After clearing Gradle transform caches (~1.5 GB was recovered), the NDK re-download and two Gradle runs exhausted all available space before the APK was written to disk. This is a machine-level hardware constraint unrelated to the application code.

3 · Specific Bugs Fixed
Bug #1
Reports never loaded into MapStateController markers list. Fixed by adding a watch<RoadReportsProvider> inside SmartRouteMap.build() with a post-frame loadReportMarkers() call.
Bug #2
New reports invisible on map after submission. Fixed as a consequence of #1 — SmartRouteMap now reacts to every RoadReportsProvider state change.
Bug #3
Marker tap had no navigation to report detail. Fixed by wiring onViewDetail: () => context.push('/reports/$id') using marker.payload (which holds the report ID).
Bug #4
Route selection didn't highlight the correct polyline. Fixed by rebuilding MapRouteGeometry list inside _RouteResultsList.build() using selectedId from the planner provider.
Bug #5
Map screen UI overlap. Fixed by separating positions: chips at bottom+8, badge at bottom+60, and suppressing both when marker info card is visible.
Bug #6
Road Reports map view missing "View details". Fixed by adding onViewDetail callback in _ReportsMapView's MarkerInfoCard.

11 · APK Build Result
⚠ APK not produced — blocked by disk space on build machine
Root cause: The C: drive (100 GB total) had 0 bytes free during Gradle compilation. The NDK download (~700 MB) and Gradle transform cache (~1.5 GB) together exhausted all available space before the dex/APK write phase.

What was verified before disk ran out:
• NDK 28.2.13676358 successfully reinstalled after the corrupted copy was removed
• Gradle picked up the project correctly
• No application-level build errors were present
• flutter analyze and all 30 unit/widget tests pass

To build on a machine with sufficient space:
flutter build apk --release
Expected output: build/app/outputs/flutter-apk/app-release.apk
Expected size: ~35–50 MB (flutter_map + google_fonts + rive are the main contributors)

Signing note: android/app/build.gradle.kts uses signingConfigs.getByName("debug") for the release build type. This produces a testable APK suitable for sideloading and device testing. For Google Play distribution, replace with a release keystore as documented in the gradle file comments. Do not use debug signing for a production Play Store submission.
12 · Remaining External Configuration & Production Requirements
ORS API Key — real routing (optional)
Create a free account at openrouteservice.org. Pass the key at build time: flutter build apk --release --dart-define=ORS_API_KEY=your_key. Without the key the app falls back gracefully to scaled sample routes.
Release signing — required for Play Store
Generate a keystore with keytool, create android/key.properties (git-ignored), and update build.gradle.kts to load signingConfigs.release. Full instructions are in the gradle file comments.
OSM tile policy — production deployment
The app uses the public openstreetmap.org tile CDN with a correct User-Agent header. For production scale, switch to a commercial tile provider (MapTiler, Stadia Maps, etc.) or self-host tiles. Attribution is correctly shown on all map views.
Supabase / backend — optional production upgrade
The architecture is ready for Supabase. Provide --dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=... to enable backend auth and real road-report persistence. Currently all data is local/demo.
